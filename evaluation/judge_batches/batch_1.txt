11. Required fact: Because Stripe signs the raw byte stream, so JSON normalization changes the payload and invalidates stripe-signature verification.
   Model answer: Here’s what this repo documents:

**Because Stripe’s `stripe-signature` is computed over the exact raw request bytes Stripe sent, not over “logically equivalent” JSON.** Signature verification replays the same HMAC using the webhook secret and the body buffer. If a proxy parses JSON and calls `JSON.stringify` again, you almost always get a **different byte sequence** (key order, whitespace, number formatting, Unicode escapes, etc.), so the computed signature no longer matches the header—even when the parsed object is the same.

The integration guide states this explicitly:

```9:15:docs/integration/webhooks.md
### ⚠️ Critical: Raw Body Requirement

The Stripe webhook endpoint **must receive the raw, unparsed request body** for signature verification to succeed. This is a hard requirement from Stripe's SDK.

The route is registered in the application **before** `express.json()` middleware, which means `express.json()` does NOT process this route. If you are writing integration tests or a proxy that forwards webhook events, you must send the raw bytes — not a parsed JSON object re-serialized.

Sending a parsed-and-re-stringified body (even if the JSON content is identical) will cause signature verification to fail with a `400` error:
```

The staging incident summary adds that **authenticity is about byte-level fidelity**, not semantic JSON equality:

```13:21:docs/incidents/2026-03-05-stripe-signature-staging-incident.md
Stripe signs the original raw bytes. The proxy changed the payload, so the service could no longer validate the `stripe-signature` header.
...
Webhook authenticity depends on transport-level fidelity, not just equivalent JSON content.
```

So: forward the **raw body stream/buffer** unchanged and pass through the `stripe-signature` header; do not parse and re-serialize in the middle.

13. Required fact: The dispatcher treats 429 as retryable, so the worker marks the job failed and reschedules it with backoff unless it has already exhausted maxAttempts.
   Model answer: Here’s what this repo does for **outbound** webhooks (the code lives in the order-management service, not a separate “frontend-only” app).

## What happens on HTTP 429

1. **`dispatchWebhook`** (`src/webhooks/dispatcher.ts`) treats **429 as retryable** (same bucket as 408 and 5xx). It does **not** treat it as a permanent failure: it returns `success: false` with `errorMessage` like `HTTP 429` and logs a warning: *"Webhook got retryable error status"*.

2. **`processWebhookBatch`** (`src/jobs/webhookWorker.ts`) then:
   - Increments the completed attempt count (`attemptCount + 1`).
   - Unless the job is **dead**, it **reschedules** the job: `status` → **`failed`**, stores `lastError`, bumps `attemptCount`, and sets **`nextRunAt`** using **`nextAttemptDate`** (exponential backoff with **full jitter** — see `src/webhooks/backoff.ts`).
   - The worker only moves a job to **`dead`** if **`attemptCount` reaches `maxAttempts`** (default **8** on the model) or the error is explicitly **non-retryable** (messages starting with `"Non-retryable"` — 429 does not).

3. On a later poll (every **5 seconds**), jobs with `status` **`pending`** or **`failed`** and `nextRunAt` in the past are picked up and tried again.

So: **429 → logged as retryable → job stays in the retry loop with backoff until success or max attempts, then `dead` (or manual replay via the admin webhook routes described in the docs).** The system does **not** honor `Retry-After` in code; scheduling is driven only by the internal backoff.

15. Required fact: Correlation IDs help logs, but they do not automatically propagate full distributed trace context across publish and consume boundaries, which is why the repo added OpenTelemetry header propagation.
   Model answer: Here’s what this repo says:

**`x-correlation-id` is only a shared label for logs.** It works well when everything is still tied to one HTTP request and Winston logs, but it does **not** carry **OpenTelemetry trace context** (trace/span IDs and parent links).

**Across RabbitMQ, that gap matters:** Without injecting and extracting OTel context on publish/consume, traces **break at the HTTP boundary**. Operators saw the inbound webhook span while RabbitMQ work looked like a **separate, orphaned trace**, so you could not rebuild a **single distributed trace tree** or **timing** for flows like Stripe webhook → RabbitMQ → downstream consumer.

The docs state explicitly that correlation ID stayed useful for **log correlation**, but the missing piece for **proper tracing** was **OpenTelemetry propagation through RabbitMQ message headers**, not the correlation ID alone (`docs/investigations/2026-03-14-rabbitmq-trace-gap.md`, `docs/guides/tracing-implementation-notes.md`, `history/issues/142-rabbitmq-tracing-context-loss.md`).
