5. Required fact: Because Stripe verifies the original raw bytes, and parsing plus re-stringifying changes the payload that the signature was computed over.
   Model answer: Here’s what this repo documents.

**Stripe signs the original raw request bytes.** The `stripe-signature` header is an HMAC over that exact payload. Verification recomputes that HMAC from whatever body bytes the order service sees and compares it to the header.

**Parsing and re-serializing changes those bytes** (even when the JSON “means” the same thing): key order, spacing, how numbers/strings are encoded, escaping, etc. can all differ from what Stripe actually sent. The incident write-up states plainly: *“Stripe signs the original raw bytes. The proxy changed the payload, so the service could no longer validate the `stripe-signature` header”* and *“Webhook authenticity depends on transport-level fidelity, not just equivalent JSON content.”*

So signature verification fails because the bytes no longer match what Stripe signed — not because the logical JSON differs.

Relevant repo notes: [`docs/integration/webhooks.md`](docs/integration/webhooks.md) (raw body requirement; parsed-and-re-stringified bodies break verification) and [`docs/incidents/2026-03-05-stripe-signature-staging-incident.md`](docs/incidents/2026-03-05-stripe-signature-staging-incident.md) (proxy parsed JSON and re-serialized before forwarding). The Stripe route is wired with `express.raw({ type: 'application/json' })` so the handler gets unmodified bytes (`src/routes/webhooks.ts`).

7. Required fact: The dispatcher marks 400 as non-retryable, and the worker treats non-retryable failures as dead immediately rather than scheduling backoff.
   Model answer: Here’s what the code is doing.

## Why HTTP 400 ends up **dead** (not retried forever)

**1. The dispatcher treats 400 as non-retryable.**

Only a small set of status codes are considered retryable; **400 is not among them**:

```15:18:src/webhooks/dispatcher.ts
// we only treat these as "real" failures that should retry.
// 4xx (except 429) means the receiver rejected our payload - retrying wont help
// but we retry anyway on 408 and 429 because those are timeout/ratelimit not logic errors
const RETRYABLE_STATUS_CODES = new Set([408, 429, 500, 502, 503, 504]);
```

For any other non-2xx status (including **400**), the dispatcher returns an error message that starts with `"Non-retryable"`:

```49:57:src/webhooks/dispatcher.ts
    // non-retryable 4xx - log it but signal success=false with no retry
    // the worker will move this to dead immediately
    logger.error("Webhook got non-retryable error, moving to dead", { ...logCtx, statusCode: response.status });
    return {
      success: false,
      statusCode: response.status,
      errorMessage: `Non-retryable HTTP ${response.status} - payload rejected`,
    };
```

So the design assumption is: **most 4xx responses mean the receiver rejected the request in a way that won’t be fixed by repeating the same delivery**, so retrying “forever” would not help.

**2. The worker moves those jobs straight to `dead`.**

`maxAttempts` is not what stops 400 here—the **non-retryable** flag does:

```50:52:src/jobs/webhookWorker.ts
    const isDead =
      completedAttemptCount >= job.maxAttempts ||
      result.errorMessage?.startsWith("Non-retryable");
```

If `errorMessage` starts with `"Non-retryable"`, the job is marked **dead** on the first failed attempt, with no backoff/reschedule.

**Summary:** HTTP 400 is intentionally **not** in `RETRYABLE_STATUS_CODES`, so the dispatcher labels the failure as non-retryable, and the worker treats that label as “dead immediately” instead of applying the normal retry/backoff path.

## Why retries were too fast in staging

Scheduling used the **stored `attemptCount` before it reflected the attempt that had just finished**. The next run was computed from that **stale** value, so backoff was **one step shorter than it should have been** (the investigation calls this out explicitly: next retry time came from the old count).
```9:17:docs/investigations/2026-03-20-webhook-retry-timeline.md
## Timeline Reconstruction
1. A job failed on its first delivery attempt.
2. The worker marked the attempt as failed.
3. The next retry time was computed from the stale stored `attemptCount`.
4. The dispatcher still exposed the human-visible attempt number as `attemptCount + 1`.
5. Operations compared the header value with the reschedule delay and noticed they did not line up.

## Conclusion
The bug was not in the jitter formula itself. The bug was in when the worker treated an attempt as completed.
```

The fix is in **`src/jobs/webhookWorker.ts`**: the worker now derives **`completedAttemptCount = job.attemptCount + 1`** and uses that for **`nextAttemptDate`**, persistence, and dead-letter checks, so backoff and dead-letter logic both use the **completed** attempt count.

```37:41:src/jobs/webhookWorker.ts

    // discovered because staging retries were coming in too fast
```

## Replay without wiping retry history
