6. Required fact: The staging incident, issue #87, the webhooks integration guide, the webhook route, and the error-handling doc together show that Stripe signs raw bytes, so semantically equivalent but re-serialized JSON still fails signature verification.
   Model answer: Here’s what this repo documents.

**Chain:** Stripe signs the **exact raw HTTP body bytes** and puts the result in `stripe-signature`. Verification recomputes the HMAC over the body the server actually receives and compares it to that header. A proxy that **parses** JSON and **re-serializes** it changes the byte stream (whitespace, key order, numeric/string encoding, etc.), so the bytes no longer match what Stripe signed—even if the JSON is logically the same.

So the failure is **signature ↔ body byte mismatch**, not wrong JSON fields. The staging incident write-up states that Stripe signs the original raw bytes, the proxy altered the payload by parse/re-serialize, and concludes that **webhook authenticity depends on transport-level fidelity, not just equivalent JSON** (`docs/incidents/2026-03-05-stripe-signature-staging-incident.md`). The integration doc says you must forward **raw bytes**, not a parsed object re-stringified, and that parsed-and-re-stringified bodies break verification even when content looks identical (`docs/integration/webhooks.md`).
