### 1. **Events may never be published (routing key is irrelevant)**

Integration docs state that publishing is **fire-and-forget** and **not required for a successful order**. If RabbitMQ is down or unreachable when the service tries to publish, **the event is dropped** (with a warning logged), while the order is still saved. If the channel isn’t ready, you get the logged warning: `RabbitMQ channel not established.
```36:44:docs/integration/events.md
## Important: Fire-and-Forget Publishing

Event publishing is **non-blocking and non-critical to the order creation response**. If RabbitMQ is unavailable at publish time, the event is dropped silently (a warning is logged). The order is still saved successfully.

This means:

- **Inventory reservation is not guaranteed** at the time `POST /api/orders` returns `201`.
- Downstream consumers operate on eventual consistency — there may be a delay before inventory is updated or payment is initiated.
- If the RabbitMQ channel is not established, a warning is logged: `RabbitMQ channel not established. Event dropped.`
```

### 2. **Wrong exchange (routing key alone isn’t enough)**

Messages are published to a **specific exchange**. The docs describe a rename: historically `order_events`, later **`order_stream`** as canonical. Code in this repo uses yet another name (`order-events` in `rabbitmqSetup.ts`). The exchange is a **topic** exchange. A consumer must bind with a **pattern** that actually matches the published routing key (e.g. `order.*` vs `order.created` vs a more specific key). A “correct” string in isolation can still be wrong for **topic matching** if the binding pattern doesn’t cover it.

**Bottom line:** The usual reasons in this repo are **no publish** (broker/channel down → silent drop), **wrong exchange name after migration**, or **topic binding pattern** not matching the published key, not merely a typo in the routing key string.

   Model answer: Here is what the repo says.

**Request-level correlation and end-to-end tracing are not the same thing.**

- **`x-correlation-id`** is applied on HTTP requests (middleware) and is used for **log correlation** within that request and when you manually pass it around. That can look “successful” for a single HTTP call.

- **Distributed traces** need the **OpenTelemetry trace context** (parent/child spans, trace id, etc.) to be carried across async boundaries. That is done by **injecting that context into RabbitMQ message headers** and **extracting it on consume**. The docs state plainly that **`x-correlation-id` does not rebuild a proper trace tree** by itself.

From the investigation and issue notes:

- Trace context was **not injected on every publish path**, and **one callback-style amqplib path dropped the active OTel context**, so downstream RabbitMQ work could show up as a **separate/orphaned trace** even when HTTP still had a correlation id and logs lined up.

So: you can see **good request-level correlation** (same id in logs for the inbound HTTP work) while **losing end-to-end traces** because **correlation id ≠ trace propagation**, and **without OTel headers (and correct context) on messages**, the async hop over RabbitMQ is invisible to the tracer’s parent/child linkage.

References: `docs/investigations/2026-03-14-rabbitmq-trace-gap.md`, `history/issues/142-rabbitmq-tracing-context-loss.md`, `docs/guides/tracing-implementation-notes.md` (lines on Winston correlation IDs vs RabbitMQ blindness).

## Why distinguish them?

Both situations can leave an order **stuck in `PENDING`**, but they are **different failure modes** with different fixes.

### Signature verification failure

- The webhook **never validates** the request, so the handler does not reliably process the event. The docs describe a **`400`** and errors like “Webhook signature verification failed” ([`docs/integration/webhooks.md`](docs/integration/webhooks.md), [`src/routes/webhooks.ts`](src/routes/webhooks.ts)).
- Typical causes are **transport / infra**: raw body not preserved (e.g. proxy or middleware parsing JSON before verification), wrong `STRIPE_WEBHOOK_SECRET`, missing `stripe-signature` header. The staging incident doc ties this to **no orders moving from `PENDING`** while Stripe retried ([`docs/incidents/2026-03-05-stripe-signature-staging-incident.md`](docs/incidents/2026-03-05-stripe-signature-staging-incident.md)).

**Debug/fix:** webhook pipeline, secrets, raw body, proxies — not “did we put `orderId` on the PaymentIntent?”

### Missing `PaymentIntent` metadata

- The docs say `payment_intent.succeeded` updates the order to paid using **`orderId` from `paymentIntent.metadata`** ([`docs/integration/webhooks.md`](docs/integration/webhooks.md)).
- **Without** `metadata.orderId`, the doc states the handler **cannot find the order**, so status **stays `PENDING` indefinitely** — even if the webhook is received and verified.

**Debug/fix:** client/checkout integration: ensure the PaymentIntent is created with the correct **`metadata.orderId`** (and that it matches the order from `POST /api/orders`).

### Summary

An engineer should separate them because **signature problems** mean “events aren’t being accepted/processed as real Stripe webhooks” (infra, 400s, retries), while **missing metadata** means “webhooks may be fine, but the payment isn’t linked to an order” (integration bug). Same stuck `PENDING` UI, **different root cause and different remediation**.
