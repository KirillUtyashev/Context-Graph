**Why retries felt “too fast” in staging (before v1.6.1)**

From `docs/investigations/2026-03-20-webhook-retry-timeline.md`, the issue was **not** the jitter/backoff formula. After a delivery failed, the worker **scheduled the next retry using a stale `attemptCount`**. The real completed attempts and the value used for backoff were out of sync: backoff was derived from the **old** count, while the outbound request still exposed the **next** attempt as `attemptCount + 1` in headers. `docs/releases/2026-03-21-v1.6.1.md` states the fix: **completed attempt counts now drive both backoff and dead-letter logic**, so scheduling matches the same notion of “which attempt this is” that operators (and headers) see.

## Why identical JSON can still break verification

**Stripe’s `stripe-signature` is computed over the exact raw HTTP body bytes**, not over “the same JSON object.” Verification recomputes the HMAC from the body your app actually receives and compares it to the header.

If an edge proxy **parses** `application/json` and **re-serializes** it before forwarding, the byte stream usually changes even when the data is logically the same: whitespace, key order, how numbers/strings are encoded, Unicode escapes, etc. The forwarded body no longer matches the bytes Stripe signed, so verification fails.

From the staging incident write-up:

```10:16:docs/incidents/2026-03-05-stripe-signature-staging-incident.md
A new proxy path parsed `application/json` and re-serialized the body before forwarding the request to the order service.

Stripe signs the original raw bytes. The proxy changed the payload, so the service could no longer validate the `stripe-signature` header.
...
Webhook authenticity depends on transport-level fidelity, not just equivalent JSON content.
```

The integration guide states the requirement explicitly:

```11:15:docs/integration/webhooks.md
The Stripe webhook endpoint **must receive the raw, unparsed request body** for signature verification to succeed. This is a hard requirement from Stripe's SDK.
...
Sending a parsed-and-re-stringified body (even if the JSON content is identical) will cause signature verification to fail with a `400` error:
```

**Short answer:** Signature verification is over **raw bytes**; “same JSON” after parse/serialize is not guaranteed to be the **same bytes**, so the HMAC no longer matches.
