11. Required fact: Because Stripe signs the raw byte stream, so JSON normalization changes the payload and invalidates stripe-signature verification.
   Model answer: Here is what the indexed codebase says (via codebase-memory-mcp only):

## Why avoid parse + re-stringify on a Stripe webhook proxy?

**Signature is over the exact raw bytes Stripe sent.** The integration doc states that the endpoint **must get the raw, unparsed body** so Stripe’s SDK can verify the `stripe-signature` header. If a proxy **parses JSON and sends it again as a string**, you are no longer forwarding the **same bytes**—even when the logical JSON matches. The doc explicitly says that **parsed-and-re-stringified** bodies **break** verification and yield errors like “No signatures found matching the expected signature for payload,” often as **400**.

A staging incident note reinforces this: **“Stripe signs the original raw bytes. The proxy changed the payload, so the service could no longer validate the `stripe-signature` header.”**

**Practical takeaway from the repo:** forward the **raw bytes** (same as using `express.raw({ type: 'application/json' })` on the receiving route so `express.json()` does not alter the body). Parsing/re-serializing can change whitespace, key order, number formatting, etc., so the HMAC no longer matches what Stripe computed.

13. Required fact: The dispatcher treats 429 as retryable, so the worker marks the job failed and reschedules it with backoff unless it has already exhausted maxAttempts.
   Model answer: Here is what the indexed code does when an outbound webhook gets **HTTP 429**.

### 1. Dispatcher (`dispatchWebhook`)

- **429 is treated as retryable.** It is in `RETRYABLE_STATUS_CODES` together with `408`, `500`, `502`, `503`, `504`.
- The POST uses `validateStatus: () => true` so non-2xx responses are handled in code, not thrown.
- For a non-2xx status in that set (including **429**), the code logs **“Webhook got retryable error status”** (warn) and returns  
  `{ success: false, statusCode: response.status, errorMessage: \`HTTP ${response.status}\` }`  
  — so for 429 the message is **`HTTP 429`**, not the “Non-retryable HTTP …” string.

### 2. Worker (`processWebhookBatch`)

- After `dispatchWebhook`, if `result.success` is false, the job is **not** considered dead just because of 429. A job goes to **dead** only if:
  - `completedAttemptCount >= job.maxAttempts`, **or**
  - `result.errorMessage` starts with **`"Non-retryable"`** (that path is for non-retryable 4xx; 429 does not use that prefix).

So for 429, **unless max attempts are reached**, the worker **reschedules** the job: it sets status to **`failed`**, bumps **`attemptCount`**, sets **`lastError`** to the HTTP message, and sets **`nextRunAt`** using **`nextAttemptDate(completedAttemptCount)`** (backoff). It logs **“Webhook job rescheduled”**.

If **`maxAttempts`** is already exhausted on that attempt, the job is moved to **`dead`** with the same error info.

**In short:** 429 is classified as a **retryable** failure; the worker **does not** drop the job to dead for that reason alone—it **re-queues with backoff** until success or **max attempts**, then **`dead`**.

From the tracing notes: correlation IDs on HTTP (`x-correlation-id`) are fine for **single-service HTTP** requests, but the service is **blind once work goes into RabbitMQ** unless something else propagates context. From the RabbitMQ trace-gap investigation: `x-correlation-id` **stays useful for log correlation**, but it **does not rebuild a proper distributed trace tree**. What was missing was **injecting trace context into RabbitMQ message headers** (and related fixes); without that, downstream work can look like an **orphaned trace** compared to the inbound HTTP span.

Issue #142 adds: the ID **is not sufficient once work leaves the process**; messages were published **without OpenTelemetry propagation headers**, so the HTTP span and RabbitMQ-side work **could not be stitched reliably** into one trace—only explicit **inject on publish / extract on consume** (plus fixing paths that dropped active context) addresses that.
