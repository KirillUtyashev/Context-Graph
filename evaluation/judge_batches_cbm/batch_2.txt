7. Required fact: The completed attempt count.
   Model answer: Here is what the indexed codebase says.

## Answer

After the **v1.6.1** fix, **completed attempt counts** drive both **dead-letter** decisions and **backoff** scheduling.

The **v1.6.1** release notes state that webhook retry scheduling was fixed so **completed attempt counts** drive **both backoff and dead-letter decisions**.

In `processWebhookBatch`, each run uses:

- **`completedAttemptCount = job.attemptCount + 1`** (the count **after** the current dispatch finishes).

That value is used to:

- **Dead letter:** treat the job as dead when `completedAttemptCount >= job.maxAttempts` (or when the error is non-retryable).
- **Backoff:** call `nextAttemptDate(completedAttemptCount)` for the next `nextRunAt`.

So the operative number is the **completed-attempt count** (incremented from the stored `attemptCount` after each finished attempt), not the pre-attempt `attemptCount` alone.

The backoff helpers (`calculateBackoffMs` / `nextAttemptDate`) take an **`attemptNumber`** that is documented as **1-indexed** (first retry = 1), which aligns with passing the completed-attempt count into `nextAttemptDate` for scheduling after a failure.

So in this codebase the “augmentation” for cross-service visibility after the RabbitMQ work is **OTel propagation into/out of RabbitMQ headers** (standard trace context carriers), not additional logic on the `x-correlation-id` middleware alone—which still only sets `x-correlation-id` on HTTP request/response (`workspace.src.middlewares.correlationId.correlationIdMiddleware`).
