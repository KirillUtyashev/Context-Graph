## Why staging Stripe webhooks failed on 2026-03-05 (despite “the same” JSON)

**Cause:** A new **proxy** on the path to staging was **parsing** `application/json` and **re-serializing** the body before it reached the order service.

**Why that breaks things:** Stripe’s `stripe-signature` is computed over the **exact raw request body bytes**. Parsing and re-serializing changes those bytes (whitespace, key order, number formatting, etc.), so the payload is no longer byte-identical to what Stripe signed—even when the JSON is **semantically** the same.

So failures were due to **signature verification** failing after the proxy altered the raw payload, not due to different business meaning in the JSON.

**Mitigation called out in the doc:** Bypass that transform for `/api/webhooks/stripe`, keep the route on **`express.raw({ type: 'application/json' })`**, and document that proxies/tests must not forward parsed-then-reserialized bodies for webhooks.

**Lesson stated:** Webhook authenticity depends on **transport-level fidelity** (exact bytes), not only equivalent JSON.

## Why verification fails after parse → re-serialize

**Stripe signs the exact raw HTTP body bytes.** Verification recomputes an HMAC over those bytes and compares it to the `stripe-signature` header. Anything that replaces the original byte stream with a new one (for example `JSON.parse` then `JSON.stringify`) usually **does not reproduce the same bytes**, even when the JSON “means” the same thing—whitespace, key order, number/string encoding, and Unicode escaping can all differ.

The integration doc states that the webhook route **must** get the **raw, unparsed body**, and explicitly warns that sending “a parsed JSON object re-serialized” breaks verification and yields errors like “No signatures found matching the expected signature for payload.” The staging incident note adds that **Stripe signs the original raw bytes**, and once the payload is altered (e.g. by a proxy), the service **cannot** validate `stripe-signature` anymore.

**Bottom line (from this repo’s docs):** verification fails because the signature is tied to the **original** body bytes from Stripe, not to an equivalent JSON value; parse + re-serialize changes the bytes, so the computed signature no longer matches.

   Model answer: Here is what the indexed backend code does.

**400 is treated as non-retryable.** In `dispatchWebhook`, only these statuses are considered retryable: **408, 429, 500, 502, 503, 504** (`RETRYABLE_STATUS_CODES`). Anything else that is not a 2xx falls through to the “non-retryable 4xx” path: it returns `success: false` with an `errorMessage` like **`Non-retryable HTTP ... - payload rejected`**, and the comments say the worker will move the job to dead.

**The worker marks the job dead immediately when that happens.** In `processWebhookBatch`, a job is dead if either `maxAttempts` is exhausted **or** `result.errorMessage` **starts with `"Non-retryable"`**. So an outbound webhook that gets **HTTP 400** does not retry forever because **400 is not in the retryable set**, and the dispatcher labels those failures **`Non-retryable`**, which the worker treats as an immediate move to **`dead`**.

## Why staging retries looked “too fast”

Staging receivers saw retries **sooner than the backoff table** suggested. The indexed investigation doc explains the chain:

1. A job failed on its first delivery attempt.  
2. The worker marked the attempt as failed.  
3. **`nextRunAt` was derived from the still-stale stored `attemptCount`** (the attempt wasn’t treated as completed before scheduling the next run).  
4. Ops compared visible attempt numbers with the reschedule delay and saw they **didn’t line up**.

The conclusion in that doc: **the bug was not the jitter/backoff formula** — it was **when the worker treated an attempt as completed** for scheduling.

The worker code itself (from `processWebhookBatch` in `webhookWorker.ts`) states the concrete mistake: **`nextAttemptDate` was driven as if the attempt index was one step behind** — “attempt 0 was scheduled like attempt 1,” so **all delays were one backoff slot off**, which is why staging looked “too fast” relative to the intended table.

## Where the fix was applied

The fix is in **`src/jobs/webhookWorker.ts`**, inside **`processWebhookBatch`**: compute **`completedAttemptCount = job.attemptCount + 1`** first, then use that for persistence, dead-letter checks, and especially **`nextAttemptDate(completedAttemptCount)`** when rescheduling failed jobs so backoff **actually grows** with the completed attempt.

Cross-checks noted in the investigation point to the same worker file and also mention **`src/webhooks/dispatcher.ts`** (attempt header behavior) and **`docs/releases/2026-03-21-v1.6.1.md`** for release packaging — the **scheduling bug fix** is anchored in **`webhookWorker.ts`** per the snippets above.
