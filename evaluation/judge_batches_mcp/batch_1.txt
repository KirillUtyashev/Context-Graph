11. Required fact: Because Stripe signs the raw byte stream, so JSON normalization changes the payload and invalidates stripe-signature verification.
   Model answer: Here is what the indexed repo content says, from the context-graph MCP `search_code` results:

**Why avoid parsing and re-stringifying the body on a proxy?**

1. **Signature is over the original bytes** — In the staging incident doc it states: *“Stripe signs the original raw bytes. The proxy changed the payload, so the service could no longer validate the `stripe-signature` header.”* So anything that alters the body (including parse → `JSON.stringify`) can change the exact byte sequence Stripe signed.

2. **Backend must verify on the raw body** — In `docs/integration/webhooks.md` it says the Stripe webhook endpoint **must receive the raw, unparsed request body** for signature verification to succeed, and that this is a **hard requirement from Stripe’s SDK**.

**In plain terms:** Stripe’s `stripe-signature` is computed over the **exact** HTTP body Stripe sent. Parsing JSON and writing it again almost always changes formatting (whitespace, key order, number/string representation, etc.), so the recomputed signature check fails even when the logical JSON is “the same.” A forwarding proxy should pass the body through unchanged (or otherwise preserve byte-for-byte identity) so downstream verification still matches Stripe’s signing input.

13. Required fact: The dispatcher treats 429 as retryable, so the worker marks the job failed and reschedules it with backoff unless it has already exhausted maxAttempts.
   Model answer: Here is what the indexed **order-management-v2** code does when an outbound webhook gets **HTTP 429** from the receiver.

## Treated as retryable

In `dispatchWebhook`, **429** is in `RETRYABLE_STATUS_CODES` (with 408 and several 5xx codes). The comment says 408 and 429 are retried as timeout/rate-limit cases, not as “bad payload” 4xx.

So the dispatcher does **not** use a 2xx result; it returns **failure** with something like `errorMessage: "HTTP 429"` and logs **“Webhook got retryable error status”** (not the non-retryable path).

## Worker: reschedule with backoff (until max attempts)

The webhook worker treats a failed dispatch as **dead** only if:

- `completedAttemptCount >= job.maxAttempts`, or  
- `result.errorMessage` starts with **`"Non-retryable"`** (used for non-retryable 4xx).

A 429 response uses **`HTTP 429`**, which does **not** start with `"Non-retryable"`, so the job is **not** dead-lettered for that reason.

Otherwise it:

1. Sets status to **`failed`**
2. Stores **`lastError`**, bumps **`attemptCount`**
3. Sets **`nextRunAt`** via **`nextAttemptDate(completedAttemptCount)`** (standard backoff from `backoff.ts` — the MCP index does not show any use of a **`Retry-After`** header for 429)

The job is picked up again when **`nextRunAt`** is due (along with other `pending` / `failed` jobs).

## If retries are exhausted

When **`attemptCount`** reaches **`maxAttempts`**, the job moves to **`dead`** with the last error message.

**Summary:** **429 → logged as retryable → job stays in the retry loop → `failed` + scheduled `nextRunAt` with backoff → repeats until success or `maxAttempts`, then `dead`.** There is no special 429-only path beyond “retryable HTTP error + exponential-style scheduling.”

15. Required fact: Correlation IDs help logs, but they do not automatically propagate full distributed trace context across publish and consume boundaries, which is why the repo added OpenTelemetry header propagation.
   Model answer: Here is what the **order-management-v2** index says about this:

## Why `x-correlation-id` is not enough across RabbitMQ

**1. It does not rebuild a distributed trace.**  
The investigation notes say that `x-correlation-id` is still useful for **log correlation**, but it **does not restore a proper distributed trace tree**. What was missing was **OpenTelemetry propagation through RabbitMQ message headers** (not just carrying a single ID).

**2. HTTP-only correlation does not follow the async path.**  
The tracing guide states that correlation IDs tied to HTTP (`x-correlation-id` on the request) work for **single-service HTTP**, but the service was **“completely blind once the message enters RabbitMQ.”** OpenTelemetry context propagation is what allows mapping **timing and linkage** along paths like **Stripe webhook → RabbitMQ → downstream (e.g. inventory)**.

**3. Work leaving the process needs more than one opaque ID.**  
Issue **142** summarizes: HTTP had `x-correlation-id`, but that **is not enough once work leaves the process**, and historically messages were published **without** OpenTelemetry propagation headers—so consumers could not continue the same trace/spans as the publisher.

**4. What the code does instead:**  
The publisher uses `propagation.inject(context.active(), properties.headers)` so **active OTel context** (W3C trace context style headers, not only `x-correlation-id`) is carried on RabbitMQ; the consumer uses `propagation.extract` to restore parent context.

**Short version:** `x-correlation-id` is a **shared label for logs**; it does not encode **parent/child spans, trace IDs, or sampling** the way OTel propagation does. Without injecting/extracting that context on RabbitMQ, you lose the **trace tree and precise timing** across the broker, even if every log line shares the same correlation string.
