15. Required fact: A proxy re-serialized the JSON body, which changed the raw bytes and broke Stripe signature verification.
   Model answer: Here is what the indexed repo says about **2026-03-05** and why things broke even when the JSON “meant” the same thing.

## Why staging Stripe webhooks failed

**Cause:** A **staging proxy** started handling traffic in a way that **parsed** the body as `application/json` and **re-serialized** it before sending it to the order service.  

**Why “identical” JSON still failed:** Stripe’s webhook signing is over the **original raw request bytes**. Parsing and re-encoding JSON usually changes **whitespace, key order, and numeric formatting**, so the bytes the backend sees no longer match what Stripe signed. Signature verification against the `stripe-signature` header then fails, even when the parsed JSON is semantically the same.

The incident doc states this explicitly: Stripe signs the original raw bytes; the proxy changed the payload, so the service could not validate `stripe-signature`. The mitigation noted there was to **bypass the proxy’s transform for `/api/webhooks/stripe`**.

Related integration guidance in the same index: webhook authenticity depends on **transport-level fidelity**, not only equivalent JSON; a parsed-and-re-stringified body can fail verification with a 400 even when the JSON content matches logically.

**Impact (from the incident):** Staging webhook tests failed for about two hours; payment success events were retried and orders stayed `PENDING` until this was fixed.
