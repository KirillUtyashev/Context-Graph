5. Required fact: Because Stripe verifies the original raw bytes, and parsing plus re-stringifying changes the payload that the signature was computed over.
   Model answer: Here is a concise answer based only on what the context-graph MCP search returned.

## Why parse-then-re-serialize breaks Stripe signature verification

**Stripe signs the exact raw HTTP body.** The `stripe-signature` header is described in the repo as a **timestamp + HMAC** checked with `STRIPE_WEBHOOK_SECRET` (`docs/integration/webhooks.md`). Verification recomputes that HMAC over **whatever bytes the handler uses as the body**. Those bytes must be the **same bytes Stripe sent** when it computed the signature.

**Parsing JSON and calling `JSON.stringify` (or any re-serialization) almost never reproduces those bytes.** The indexed docs state explicitly that for proxies or tests you must forward **raw bytes**, **not** a parsed JSON object re-serialized (`docs/integration/webhooks.md`). The staging incident note adds: **“Stripe signs the original raw bytes. The proxy changed the payload, so the service could no longer validate the `stripe-signature` header.”** (`docs/incidents/2026-03-05-stripe-signature-staging-incident.md`).

So the failure is a **byte-level mismatch**: the signature is over Stripe’s original payload; a round-trip through a JavaScript object changes things like key order, spacing, and other serialization details, so the HMAC no longer matches.

**What the order service expects:** the webhook route is wired so the body stays raw (`express.raw({ type: 'application/json' })`), with comments that **`express.json()` would “corrupt” the body** for verification and that the **raw body is needed for signature verification** (`src/routes/webhooks.ts`). The integration doc also says the endpoint **must receive the raw, unparsed request body** for verification to succeed (`docs/integration/webhooks.md`).

**Bottom line:** Signature verification fails because it is cryptographic verification over **exact bytes**; parse → re-serialize replaces Stripe’s bytes with a **semantically similar but not identical** encoding, so verification fails even when the JSON “means” the same thing.

## Why HTTP 400 ends up **dead** (not retried forever)

**1. The dispatcher does not treat 400 as retryable**

In `dispatchWebhook`, only certain status codes are considered retryable (`408`, `429`, `500`, `502`, `503`, `504`). The comments say that most **4xx** responses mean the receiver rejected the request and that retrying would not help; `408` and `429` are exceptions.

For any other non-success status (including **400**), the code returns a failure whose `errorMessage` starts with **`Non-retryable HTTP … - payload rejected`**.

**2. The worker moves those jobs straight to `dead`**

In `processWebhookBatch`, after a failed dispatch, a job is considered dead if either:

- the completed attempt count has reached `maxAttempts`, **or**
- `result.errorMessage` starts with **`"Non-retryable"`**.

So for a **400**, the error message matches the second condition on the **first** failed attempt. The job is set to **`dead`** immediately; it is **not** rescheduled with backoff.

**Summary:** Retries are **not** infinite for webhook delivery: retryable statuses are a fixed set, and **400** is explicitly treated as a **non-retryable** client/receiver rejection. The worker interprets that via the **`Non-retryable`** error prefix and marks the job **dead** without further automatic retries. (Docs also mention a **max attempts** cap for cases that *do* retry.)

## Why staging saw retries too fast

The investigation doc (`docs/investigations/2026-03-20-webhook-retry-timeline.md`) says staging receivers saw **bursts of retries earlier than the backoff table predicted**. The concrete bug: **the next run was scheduled using a stale `attemptCount`** — i.e. the code advanced the count **after** using it for `nextAttemptDate`, so backoff was computed as if fewer attempts had completed than actually had, so delays stayed **too small** and retries looked “too fast.” The worker even notes this was **discovered because staging retries were coming in too fast** (`src/jobs/webhookWorker.ts` around the fix comments).

## Where the fix was applied

The fix is in **`src/jobs/webhookWorker.ts`** (notably in `processWebhookBatch`): compute **`completedAttemptCount = job.attemptCount + 1` first**, then use that for **`nextAttemptDate(completedAttemptCount)`**, dead-letter / max-attempt checks, and persisting `attemptCount`, with comments that the old order was wrong (`// FIX: was doing job.attemptCount + 1 AFTER using it for nextAttemptDate` and `// use completedAttemptCount for backoff so the delay actually grows`).

Release **`docs/releases/2026-03-21-v1.6.1.md`** summarizes it as: webhook retry scheduling now uses **completed attempt counts** for **both backoff and dead-letter** decisions.
