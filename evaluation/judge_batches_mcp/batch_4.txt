## Why a proxy can break Stripe webhooks even if the JSON “looks” the same

**Chain:** Stripe computes the webhook signature over the **original raw HTTP body bytes** → your service checks that signature using the body it receives → a proxy that **`application/json`-parses and then re-serializes** the body before forwarding does **not** preserve those bytes, so verification fails.

From the staging incident doc (via `search_code`):

1. A proxy path **parsed** `application/json` and **re-serialized** the body before forwarding to the order service.  
2. **“Stripe signs the original raw bytes.”** After that transform, the service could no longer validate the `stripe-signature` header.

The integration webhook doc adds the operational rule (same MCP search): for tests or a proxy you must **send the raw bytes**, **not** a parsed JSON object that was re-serialized.

**Why “same fields” is not enough:** signature verification is tied to the **exact byte sequence** of the body. Parse + stringify typically changes things like whitespace, key order, and sometimes numeric/string encoding—so the logical JSON can match while the **bytes** differ from what Stripe signed. That is the failure mode the repo documents.
