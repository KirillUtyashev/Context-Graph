## Why request correlation can look fine while end-to-end traces break at RabbitMQ

**They solve different problems.** Request-level correlation here is mainly **`x-correlation-id`** on HTTP: it is assigned in middleware, echoed on the response, and logged (see matches under `src/middlewares/correlationId.ts` and `docs/integration/auth.md`). ## Why a proxy can break verification even when JSON “looks the same”

**Stripe signs the original raw request body bytes**, not the abstract JSON object. Your backend verifies by recomputing an HMAC over **the same bytes** Stripe used. If an edge proxy **parses** `application/json` and **re-serializes** before forwarding, the **byte sequence** of the body can change even when the parsed data matches (whitespace, key order, number/string encoding, Unicode escapes, etc.). The `Stripe-Signature` header was computed over Stripe’s original bytes, so any byte-level change makes verification fail.

The integration docs in this repo spell that out explicitly: the webhook route **must get the raw, unparsed body**, and **“[s]ending a parsed-and-re-stringified body (even if the JSON content is identical) will cause signature verification to fail.”** The staging incident note adds that a proxy path that parsed JSON and re-serialized before forwarding broke validation because **“Stripe signs the original raw bytes”** and the proxy had effectively changed the payload at the byte level.

**Practical takeaway:** forward the **raw body bytes** (and the `Stripe-Signature` header) through the proxy; do not parse and `JSON.stringify` the body for webhook routes.

## Why this did not make audit logging “transactional”

Two separate ideas show up in the indexed code:

1. **Best-effort audit** — The feature doc notes there is **no strict guarantee the log write succeeds** (search hit on `docs/features/audit-logging.md`: *“No strict guarantee of log write (best-effort)”*).
