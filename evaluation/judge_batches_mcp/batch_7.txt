1. Required fact: The completed attempt count.
   Model answer: Here’s what the context-graph MCP results show.

## Answer

After the **v1.6.1** fix, **completed attempt count** drives both **dead-letter** decisions and **backoff** scheduling.

The release note states: webhook retry scheduling was fixed so **completed attempt counts** drive **both** backoff and dead-letter decisions (`docs/releases/2026-03-21-v1.6.1.md`).

In `webhookWorker.ts`, that is implemented as **`completedAttemptCount`**, defined as `job.attemptCount + 1` after `dispatchWebhook` returns (so it reflects the attempt that just finished, not a stale count used before incrementing).

- **Dead-letter:** the job is marked dead when `completedAttemptCount >= job.maxAttempts` (or the error is non-retryable).
- **Backoff:** the next run uses `nextAttemptDate(completedAttemptCount)` so the delay matches the number of **completed** failures.

Comments in the same file describe the bug the fix addressed: previously `attemptCount + 1` was applied **after** using the count for `nextAttemptDate`, which shifted every backoff slot; the fix aligns scheduling with **completed** attempts.
